## Architecture

Request path: HTTP route (`api/http.py`) or xcore `@action` (`plugin.py`) → builds an immutable `RequestContext` (`context.py`) → `DocumentService` (`document.py`, the only door to data; orchestrates permissions and hooks) → `Query(session, ctx, tables)` (`query.py`, the only place SQL is built) → generic table `xdt_document` (`db/tables.py`).

Rules that span files:

- **Definition-driven.** `schema.py` (Pydantic, `extra="forbid"`) → `builder.py` (a `create_model` write validator per DocType) → `registry.py`. No per-DocType code. The schema **rejects** blocks the engine doesn't enforce yet (today: series naming, only `naming: hash` is accepted) instead of ignoring them; allow a block only in the commit that implements it.
- **Permissions deny by default** (`permissions.py`). xauth already resolves roles and grants per request, so a DocType does **not** restate an RBAC matrix: with no `permissions` block, grants come from `module` + the DocType name (`schema.conventional_grant`): `read` → `<module>:<doctype>:read`, `write` **and** `create` → `…:write` (xauth's "Créer/modifier"), `delete` → `…:delete`. An explicit `permissions: {read: [...], write: [...], create: [...], delete: [...]}` replaces the convention **per action** (an entry is a grant string, or `{grant, if_owner, description, tenant_grantable}`; `[]` closes the action for everybody). Grants are checked against `principal["permissions"]`; **role names never count** (free text per tenant in xauth; `role:x` is rejected with an explanation). A `Scope` per (user, action) is compiled once and has two interpreters that must stay equivalent: SQL in `Query` (reads/updates/deletes, never filtered after the fact) and Python `Scope.allows` for the *written* value; `tests/unit/test_permissions_matrix.py` checks both against an independent in-memory oracle. No action granted → 403; document outside the READ scope → 404 (indistinguishable from missing); update/delete require read access. `match` is **frozen** (`schema.MATCH_ENABLED = False`: xauth's `user` carries no attributes); code and tests stay, tests flip the flag with `monkeypatch`; its planned replacement is an auth scope (`process/phase1.md` §7). `Query` takes a **required** `scope`; the system context uses `Scope.everything`. `module` is the grants' namespace: `[a-z0-9_]+`, not one of xauth's reserved namespaces.
- **Grants have one source: the DocType YAML.** `GrantCatalog` (`grants.py`, exported as the service `doctype_grants`) lists the grants the DocTypes need in `rbac.declare` format; the **owning plugin** (named like the `module`) passes `for_plugin(self.ctx.name)` to a **single** `rbac.declare` (xauth deactivates a plugin's grants missing from the list it receives). xcore-doctype never emits `rbac.declare` itself. **`default_roles` (auth review of 26 Oct 2026)**: a declared grant goes to xauth's PLATFORM `admin` role and to nobody else, so `GrantSpec.as_declaration` asks for `default_roles: ["tenant_admin"]` on every **delegable** grant — without it, whoever creates an organisation owns it but cannot read or write a single document in it until a platform admin unblocks them. A closed grant (`tenant_grantable: false`: the stock ledger, the bins) is NOT given by default either. Delegable and owner-by-default are two different questions: `iam` deliberately asks for `default_roles` on ALL its grants, because managing access is not delegable (`iam:role:write`) yet the owner must have it (`tests/support/plugins/iam/src/main.py`).
- **Hooks** (`hooks.py`, orchestrated in `document.py`). Trusted hooks are coroutines registered by name in a per-instance `HookRegistry`, exported to other plugins as the service `doctype_hooks`; hook names are registry keys, never imported paths (D16). Save order: permission → hook availability → schema + written-value check → `action:` hooks (sandboxed plugins, **outside** any transaction, tenant/principal passed explicitly, output revalidated like client input) → transaction with trusted `validate` then `before_save` → commit → `after_save` + EventBus event without document content. A hook referenced but not registered **refuses the save** (503), never skipped. `validate`/`before_save` are called directly because `EventBus.emit` swallows errors. Never log with a field named `msg` (xcore's logger is `error(msg, **fields)`).
- **Conditions (`expr.py`, D22).** `depends_on`, `mandatory_depends_on`, `read_only_depends_on` are strings in the YAML, parsed by the ONE parser in `expr.py` (no `eval`) into a whitelisted JSON AST that `/meta` sends and `ui/src/lib/expr.ts` evaluates; the server re-evaluates the same AST on write (`builder._condition_errors`). Same type-strict semantics in both languages (`1 == true` is false, strings compare by code point, `0`/`""` falsy): change one side and the shared vectors fail. A field with `depends_on` is required only when visible; `read_only_depends_on` is evaluated on the **stored** document and only for client input (hook output is exempt), so the Desk evaluates it on the saved values for an existing document.
- **Filters are typed per field** (`FILTER_OPS`): no ordering on Text/Select/Link (collation differs per backend), `like` is case-insensitive with escaped wildcards, `in` ≤ 100, `!=` also matches NULL, `name` is filterable as Text. `GET /search/{doctype}` feeds Link autocompletion; the Desk resolves Link titles with a `name in [...]` list call.
- **The Desk is served by a separate PUBLIC router** (`api/desk.py`, `<plugin_prefix>/xcore-doctype/desk/`) mounted beside the protected API router: static files only (path traversal and symlink escapes refused, strict CSP, `assets/` immutable), plus `config.json` (API base derived from the request URL, optional `login_url`: the sentinel `auth` means `<prefix>/auth/login`, derived from the request prefix so it follows `plugin_prefix`). The SPA holds its token in `sessionStorage`, talks through a replaceable `Transport` (`ui/src/lib/transport.ts`, for a future Tauri port), uses hash routing and sends `X-Tenant-ID` read from the token claims (D17).
- **Series numbering (`naming.py`, D7/D13).** `naming: {series: "FA-{YYYY}-{#####}"}` → `FA-2026-00001`. The counter row is `(tenant_id, doctype, resolved series)` and is incremented by ONE `INSERT … ON CONFLICT DO UPDATE … RETURNING` (`Query.next_number`) **inside the document's transaction, as the last step before the insert**: no gap when anything fails, no duplicate under concurrency (mutation-checked on SQLite and PostgreSQL), at the price of serialising creations of one series until commit. Consequences: hooks see `event.name is None` on a series DocType's creation; numbers are never reused after a delete. Date parts use `doctype.timezone` (default UTC).
- **Links are checked, not just typed.** On write, every *changed* Link value (top-level or inside a table row, path `items.0.item`) must exist in the tenant AND be readable by the caller; unreadable looks exactly like missing (`link_not_found` 422). On delete, `DocumentInUse` (409 `document_in_use`) when any document or table row of the tenant still cites it (references are looked up WITHOUT the caller's scope; the answer names DocTypes and fields, never documents). Integrity has no foreign keys: PostgreSQL row locks do the work (`FOR KEY SHARE` while linking, `FOR UPDATE` before the reference scan on delete; `tests/unit/test_links.py::TestRace` pauses transactions to prove it); SQLite has no row locks, so a narrow window between check and delete remains (documented, those tests skip on SQLite). `registry.validate_links()` makes an unknown Link target a load error. `target_status` on a Link/DynamicLink restricts the target's `docstatus` (422 `link_status`): judged on every changed link (rows counted as a multiset: one old occurrence excuses one new one), AGAIN at submit for every constrained link with the submitter's read scope (bulk submit too), on `tx` writes (500 `hook_invalid_write`), never on the values an `amend` copies (existence and readability are); the Desk's autocompletion sends `docstatus=…` to `/search` (`lib/docstatus.allowedDocstatus`, `LinkField` prop `statuses`) and `LinkPreview` shows the target's state. A concurrent cancel is not blocked by the link check's lock (equivalent to link-then-cancel, documented in `_check_links`). **`link_filters` (D29, `process/programme.md` §1.1)**: `link_filters: {pays: "$pays", actif: true}` on a Link restricts what may be chosen — a literal, or `$field` read from the SAME container (the document, or the ROW for a table field; no `parent_`). Unlike Frappe it is NOT just a UI hint: `document._check_link_filters` enforces it on write (`link_filtered` 422, distinct from `link_not_found`), on changed links only, with an empty source field restricting nothing; `/search?filters=` applies the same so the Desk only offers what a write would accept (`lib/form.resolveLinkFilters`). Mistakes are LOAD errors (`registry._check_link_filters`: the target must have the field, a literal goes through the target's own `coerce_filter`, a `$field` must match the filtered field's type). One interpreter: `coerce_filter` + `memory.select` (the Python twin of the SQL filters). Never on a DynamicLink.
- **Child tables.** A `Table` field's `options` names an `istable: true` DocType; its rows are a JSON array inside the parent (≤ 500 rows, empty list ≡ absent, validated per row with the child's strict model, errors addressed `items.0.qty`). A child has no routes, rights, hooks, module, layout, title, series, nested tables or conditions (all refused at load) and answers 404 `doctype_not_found` like an unknown DocType. The registry loads children first (`load_dir` sorts them; `register` requires them registered before the parent). Tables cannot be filtered, sorted or used in conditions. `/meta` embeds the child fields under `children`.
- **History (`versions.py`).** `xdt_version` rows (`track_changes`, default true) are written in the SAME transaction as the document: `create` = diff against nothing, `update` = changed fields only (a no-op update writes nothing), `delete` keeps the deleted content and owner. `GET /history/{doctype}/{name}` needs read access to the document; for a deleted one it judges the read scope on the stored snapshot. History is kept per GENERATION of a name (C2): each `delete` closes one (`Query._deletions`/`_generation`), an existing document shows only the entries after the last deletion of its name (a document reusing a deleted name never inherits its history), a deleted name shows its last generation, someone outside the read scope sees only their own deleted generation, and `rename` moves only the live generation. Retention: `max_versions` (default 25) keeps the newest entries of the generation being written, in the same transaction; `submit`/`cancel` entries are never purged by count (`KEPT_ACTIONS`); older generations and old entries go only BY AGE through the operator action `ops.history.purge` (see Manifest).
- **Business plugins bring their own DocTypes** (`registry.DocTypeChannel`, service `doctype_registry`): `load_dir(self.ctx.name, dir)` in `on_load` (then optionally `load_workspaces`, `load_extensions`, `load_desk`: see "Plugin extensions"), `unregister_owner(self.ctx.name)` in `on_unload`. Every DocType's `module` must equal the plugin name (children, which have no `module`, belong to the plugin that brings them), so a plugin cannot write into another's grant namespace; a plugin name that is not `[a-z0-9_]+` owns nothing. Loading is all-or-nothing and validates Link targets of the newcomer only (so Link targets must come from the plugin itself or one it `requires`) — unless **`load_dir(owner, dir, peers=True)`** (modules that cite each other in a CYCLE, like the ERP's 23 modules: one plugin per module, any load order, `tests/unit/test_peer_modules.py` loads the real `doctypes/` that way and compares with a single load): a Link to a peer not loaded yet makes the type INCOMPLETE (`registry.incomplete`: readable, every write refused 503 `doctype_incomplete` naming the missing peer, checked in `DocumentService._require_hooks`, the write choke point, and so for `tx` too); a parent whose `Table` child comes from an absent peer WAITS (`registry._waiting`, invisible, its grants still counted by `GrantCatalog`, a workspace may cite it) and registers when the child arrives (`DocTypeChannel._welcome` → `registry.settle`); on each arrival the target-dependent checks (fetch, link_filters, units, target_status, created_from) are redone for every type citing the newcomer (`registry.citing`/`link_problems`) and a failure BREAKS that citing type (`mark_broken`, writes refused, logged) instead of failing the newcomer's load; a peer leaving puts the parents that used its tables back to wait. Without `peers` an unknown target stays a load error (typos). **`load_dir` walks SUBDIRECTORIES** and its children-first sort covers the whole tree, which always suffices (a child cannot hold a `Table` field, so it is a leaf of the parent→child graph and no cycle can exist): a large set can be filed one folder per module and still load in one call, and a parent may cite a child of another folder without any folder order to find. Every file in the tree is read as a DocType — a plugin's workspaces live BESIDE its doctypes folder, never inside it. Ownership is by the name the plugin passes (like `doctype_hooks`): it prevents mistakes, not a hostile trusted plugin. `doctypes_dirs` stays for the operator's own DocTypes (free `module`, and ONE `validate_links()` once every listed dir is loaded, so those dirs may cite each other mutually); the shipped manifest sets none. The `rbac.declare` source-forcing fix (xcore + xauth) is still deferred.
- **Submittable documents (`submittable: true`, `document.py`, phase A).** `docstatus` is a real column of `xdt_document` (0 draft, 1 submitted, 2 cancelled; `amended_from` beside it), never a key of `data` (a payload cannot set it). `POST /doc/{dt}/{name}/submit|cancel` (body `{version}`) and `POST …/amend`, mirrored by the actions `doc.submit|cancel|amend`. Two more permission actions, `submit` and `cancel` (grants `<module>:<doctype>:submit|cancel`), exist ONLY for a submittable DocType (declared to auth only then; `write` never implies them; amending needs `create` + `read`). A submitted or cancelled document is **frozen**: `Query.update`/`delete` carry `docstatus = 0` in their WHERE (409 `document_locked`), only a draft is deleted. A transition is one conditional `UPDATE … WHERE version=? AND docstatus=?` (`Query.transition`), executed FIRST in the transaction: a replayed or simultaneous submit passes once (409 `invalid_docstatus` for the others, hooks run once) and on SQLite that write is what takes the database lock before any hook reads (`test_submit.py` mutation-checks it). Then the history entry (`submit`/`cancel`, diff of `docstatus`), then the hooks, then the EventBus event `doctype.<name>.after_submit|after_cancel` (no content). `submit` re-validates the stored draft against the CURRENT definition. `amend` copies a cancelled document into a draft named `<name>-1` (the next suffix for an amendment of an amendment); a document is amended once (`already_amended`, the unique name enforces it under concurrency). A submittable DocType must keep `track_changes` (who submitted/cancelled is the point). `docstatus` is filterable (`{"docstatus": 1}`, `["in", [0,1]]`) and sortable. Existing databases gain the two columns at startup (`db/access._add_missing_columns`: additive only, nullable or with a default).
- **Workflow (`schema.WorkflowDef`, `process/programme.md` §3.2).** A DocType declares its business automaton IN ITS OWN YAML (`workflow: {states, transitions}`, beside `fields`). ONE automaton, not two: a state declares the `docstatus` it imposes (`draft|submitted|cancelled`), so a transition moves state AND docstatus together — « Approuvé » on a cancelled document cannot exist. The first state is where a new document starts (`Query.insert(workflow_state=…)`); the state is a real COLUMN (`xdt_document.workflow_state`, nullable, added by the additive startup migration) because `Query.workflow_transition` is a conditional UPDATE on (version, state): two simultaneous approvals, only one passes. A transition is opened by a GRANT (`<module>:<doctype>:workflow_<action>` by convention, declared to auth like the others; `role:…` and `@authenticated` refused at load) and may carry `not_owner: true` (separation of duties: 403 `not_owner`, the author never approves their own document) and `condition:` (the `expr.py` language, compiled once into `CompiledDocType.transition_conditions`, judged on the STORED document by the single interpreter `DocumentService._transition_open`): a business rule, not a right — a false condition hides the action from `/transitions` AND refuses the write (422 `transition_condition`), and since the write is conditional on (version, state) a document changed in between gives a version conflict, never a transition judged on content nobody read. Same load refusals as `depends_on` (unknown field, Table, Password/JSON, Decimal). A state that submits or cancels requires `submittable: true`, and then `/submit` and `/cancel` are REFUSED on that DocType (409 `workflow_transition_required`, naming the transitions to use) — letting them through would bypass approval. Reaching a submitting/cancelling state runs the ordinary `on_submit` / `before_cancel` / `on_cancel` tx hooks and writes the history entry under the closed vocabulary (`submit`/`cancel`, never purged by count; otherwise `update` with the state diff). Load errors: an unreachable state, two transitions with the same action, a transition to itself or to an unknown state, a workflow without `track_changes`, on a child/single/virtual DocType. `POST /doc/{dt}/{name}/transition` (`{action, version}`) and `GET /transitions/{dt}/{name}` (what THIS caller may do on THIS document now — the Desk cannot judge it: the xauth token carries no grants and `not_owner` depends on the document). Desk: `FormView` asks `api.transitions(...)` whenever the record's version changes and renders ONE button per open action (`flow-<action>`, confirmation always, icon and danger tone from the target `docstatus`), never « Soumettre » — `transitionsFor` returns no submit/cancel for a workflow DocType (the server refuses them), only `amend`, which is a creation. The status pill shows the WORKFLOW state (`data-state`) with the tone of the document's docstatus; the just-returned record wins over the last `/transitions` read. The state is a system column like `docstatus`: filterable (`builder.SYSTEM_FILTERS`, Text), sortable (`query.SYSTEM_SORTABLE`) and groupable in an aggregate, refused with `no_workflow` on a type that has no workflow (`aggregation.validate_filters`); the list shows it in the status column and its `SelectButton` offers the workflow's STATES instead of Brouillon/Soumis/Annulé (`ListView.flowStates`, filter `workflow_state`, never both at once). Not done yet: a per-organisation layer (the workflow lives in the YAML only).
- **Transition hooks (`on_submit`, `on_cancel`) and `HookEvent.tx`.** Trusted only (an `action:` hook cannot join a transaction), they run INSIDE the transaction of the transition, so a refusal (`DocumentValidationError`) undoes the state AND everything the hook wrote. `event.tx` (`hooks.HookTransaction`, implemented by `document._Transaction`) is the ONLY way a hook writes: `get(doctype, name, lock=)`, `create(…, name=)`, `ensure(…)` (atomic create-if-absent, `ON CONFLICT DO NOTHING`), `update(…, version)`, `today` (organisation timezone). No permission is checked (trusted code) and links are checked on existence only, but every write is validated like any other (strict types, links, numbering) and historized under the submitting user. **The written DocType keeps its rules** (`_Transaction._prepare`, `tests/unit/test_tx_hooked.py`): its trusted `validate`/`before_save`/`before_insert` run inside the same transaction (a refusal undoes everything), its `after_insert`/`after_save` after the commit (`_TxWrites` → `DocumentService._settle`, never on rollback); a type with `action:` hooks stays refused (`hook_not_supported`: sandboxed, outside any transaction), a missing hook refuses (503). `tx.update` on a SUBMITTED document changes only its `allow_on_submit` fields (checked AFTER its hooks, a frozen field changed = 500 `hook_invalid_write`) and runs its `on_update_after_submit` (nested `_tx_hooks`, `depth`); cancelled = 409 `document_locked`. That is how a submitted payment updates its submitted invoice's outstanding amount. Hooks writing each other in a loop stop past `MAX_TX_DEPTH` (500 `hook_recursion`). Invalid data from a hook is a hook defect (500 `hook_invalid_write`), not a 422. A hook that reads then writes MUST lock (`tx.get(..., lock=True)`: `FOR UPDATE` on PostgreSQL; SQLite has no row lock and relies on the state write being first) and should take several locks in a fixed order (deadlocks).
- **`Decimal` fields (`decimals.py`).** Stored as a canonical STRING with exactly `decimals` digits (`"12.500"`, `decimals` mandatory 0-9), never a JSON number: a float is refused (`0.1 + 0.2`), as is any value needing more decimals (no silent rounding), more than 18 digits, an exponent, `+`, NaN. Code that computes uses `decimal.Decimal(value)`; `canonical()` also accepts a `Decimal`. Filters/sorts cast to `NUMERIC` (`as_numeric`; SQLite compares as doubles, exact to ~15 digits). A Decimal cannot appear in a condition. The Desk keeps it a string end to end (`ui/src/lib/decimal.ts`, same vectors: `tests/vectors/decimal_cases.json`); the comma of a French keyboard is normalised, list filters on a Decimal separate with `;`.

Desk side: `ExtensionHost` (one per Desk, injected as `EXTENSIONS`) holds what each extension registers in `setup(desk)` (routes `#/x/<plugin>/…`, sidebar links, form actions/panels, list actions, `extension` workspace blocks `{component: <plugin>.<name>, props}` whose component gets TWO props `config` (the block's `props`, never spread: an undeclared key would fall on its root element) and `label`, palette commands, `styles.add(href)` same-origin only), `loader.ts` loads them one by one before the first navigation (contract check: same `name`, `apiVersion: 1`; 8 s timeout; a failure drops everything the extension registered and shows ONE toast), every extension component is wrapped in `ExtensionSlot` (provides `useDesk()`, error boundary), `when()` that throws hides, an action that throws becomes a notification, `PluginClient` reaches only `<prefix>/<plugin>/…` with the Desk's session (`pluginPath` judges the path as the WHATWG parser will: control chars, `#`, `%2e%2e`, `..?` refused). Server side an `extension` block's `props` keys are `[a-z][a-z0-9_]*`, the block is never content ON ITS OWN (a workspace where the user reads nothing stays hidden), and an override may move/remove/resize one but never add one or change its component/label/props (`extension_block_not_offered`). `desk/index.html` gets the same headers as `desk/`. Form panels/actions are evaluated only for the document the page shows (`FormView.extContext` is null while loading), `reload()` is guarded by `loadTicket`, `ExtensionSlot` retries when its component/props change. The `sales` fixture ships one (`tests/support/plugins/sales/desk/index.js`, inert unless allowed); `ui/e2e/extensions.e2e.mjs` proves it under the real CSP.
- **Explicit context.** The service never reads ContextVars (D20). `tenant_id`/`owner` never come from payloads. HTTP routes bypass xcore's pipeline (no `PermissionEngine`, no ContextVars), so every route depends on `http_context`, also at router level.
- **Tenancy is a column** (D3). `Query._scope()` is the single choke point that adds `tenant_id`; no method takes a raw tenant. `tests/unit/test_query_leak.py` fails if a public `Query` method has no leak scenario, and also asserts the emitted SQL binds only the caller's tenant. Add a scenario when adding a method. The tenant must be covered by a principal claim (D17); `X-Tenant-ID` alone is untrusted.
- **Writes are strict, reads tolerant.** No coercion (`"12"`, `1`→bool rejected), canonical ISO dates only, **no NaN/Infinity** (a stored NaN breaks response serialization for the whole tenant). Secrets: on a Password field the mask `********` means UNCHANGED everywhere a value is compared (`sealing.kept`: read_only, set_only_once, frozen fields, like `_seal`); a client value starting with the sealed prefix `enc:v1:` in a NON-secret field is refused (422 `sealed_prefix`) unless it is the stored value sent back unchanged. Updates replace `data` and require `version` (UPDATE … WHERE version=?; rowcount 0 → 404 or 409).
- **Portability lives in `query.py`.** JSON filters/sorts use SQLAlchemy `as_string/as_float/as_boolean`, `NULLS LAST`, `name` as tie-break. Known gap: text sort follows each backend's collation (SQLite binary vs PostgreSQL locale).
- **Async DB only** (D11). `ensure_async_database` opens a real session because `get_service("db")` may be a `TenantAwareDB` wrapper; config needs `type: sqlite+aio` (or `postgresql+aio`), plain `sqlite` is the sync adapter.
- **No module-level state** (D8). Registry, MetaData, service and router are created in `on_load` and released in `on_unload`. Don't implement `on_reload`: xcore calls it on the *old* instance before unloading, then builds a new instance and calls `on_load`.
- **Errors don't leak.** `Plugin._run` logs unexpected exceptions and returns `internal_error`; xcore would otherwise return `str(e)` (SQL and bound parameters included). Hook failures map to `hook_rejected` 422, `hook_invalid_result` 502, `hook_unavailable` 503, `hook_timeout` 504, `hook_payload_too_large` 413 (see `process/phase1.md`).

Tests: `tests/unit` (the `db` fixture runs every DB test on SQLite and, if configured, PostgreSQL) and `tests/integration` (`boot_host` starts a real `Xcore` from the repo's `integration.yaml` in a tmp dir; read plugin routes through `host.plugin_routes()`, which uses OpenAPI because FastAPI 0.14x `app.router.routes` holds path-less `_IncludedRouter`s). `boot_host(hook_plugins=True)` also starts a trusted plugin that registers hooks and a **real sandboxed plugin** (a subprocess, ~1 s to start; the suite takes ~1 min). A sandbox worker's startup is bounded by `min(5 s, the plugin's resources.timeout_seconds)`: keep test plugins at xcore's default 10 s or activation fails under load (the harness retries the load and says so).

## xcore integration facts

- **`main.py` must call `xcore.setup(app)`**: only it installs `TenantMiddleware`; `boot()` does not. Without it `request.state.tenant_id` is never set and the plugin answers 500 `tenant_middleware_missing`.
- **Set `tenancy.isolate_db: false`.** HTTP routes never set the tenant ContextVar, so `TenantAwareDB` isolates on `default` for HTTP but on the real tenant for IPC; with existing tenant schemas HTTP and IPC diverge. `on_load` warns when it sees a `TenantAwareDB` on PostgreSQL.
- **xcore doesn't expose `tenancy.enabled` to plugins**: `doctype.enforce_tenant_binding` (default true, fail-closed) is set by hand and must be false only if xcore tenancy is off.
- **Discovery is a directory scan** (`plugins.directory: ./app`); no entry points exist yet. The host symlinks `app/xcore-doctype` → `src/xcore_doctype/plugin_dir` (plugin.yaml + shim `src/main.py`). The shipped wheel contains that folder but xcore won't discover it. `strict_trusted: true` blocks the unsigned plugin; the dev config sets it to false.
- **Manifest** (`plugin_dir/plugin.yaml`): `permissions` (`doc.*`, `meta.*` → `execute`; absent means `deny_all`), `allowed_callers: ["*"]`, and the `doctype:` block read through `self.ctx.config["doctype"]`. Operator actions live under `ops.*` (`ops.history.purge`), which the shipped manifest does NOT open (xcore answers `permission_denied` until the operator adds it to their copy; a commented line shows how) AND which require a token carrying `cross_tenant_grant` (`context.ipc_operator`): never put an operator action under `doc.*`. Per-deployment settings live in the operator's installed copy of that manifest (`xcore-doctype install` never overwrites it without `--force`); `doctypes_dirs` is relative to the launch directory.
- **Auth = xauth (`app/auth`, copied from orchestra-backend and adapted: `process/xauth.md`).** `decode_token` returns `AuthPayload(sub, roles=[names], permissions=[grants of the tenant], user={email, tenant_id})`; `sub` and the `tenant_id` claim are UUIDs. Grants are announced with `rbac.declare` (first segment must be the declaring plugin's name, `[a-z0-9_]+`; reserved: admin rbac auth tenants user license plugins); xauth gives them to its `admin` role as they arrive, so **xauth must load BEFORE the plugins that declare** (they `requires: [..., auth]`; an event emitted before xauth listens is lost). xcore-doctype only *checks* grants and logs the ones its DocTypes cite (`xcore-doctype loaded`, field `grants`). `cross_tenant_grant` is looked up in `permissions` only (`admin:*` is xauth's platform admin; the default is unchanged). xcore only expands `${VAR}` in a manifest `env:` block when the variable EXISTS (no default syntax; a missing one rejects the plugin).
- **Login = identifier (username OR e-mail).** The Desk's login field is plain text; `session.login(identifier, …)` sends `{username}` or `{email}` by the presence of `@`, xauth's `LoginRequest.identifier` resolves it (`UserRepository.get_by_identifier`: e-mail compared case-insensitively, username lowercase). A username is 3-32 chars `[a-z0-9._-]`, never contains `@` (so no ambiguity), unique (`xauth_users.username` + index `ux_xauth_users_username`), chosen at registration (optional) or in Mon compte (`PATCH /account/username`: password + OTP when MFA is on); the seeded admin gets `ADMIN_USERNAME` or the local part of their address. An existing xauth database gains the column at startup (`app/auth/src/utils/db_upgrade.py`, additive and idempotent: extend `ADDED_COLUMNS` for the next one). xauth's own rate limit (5 logins / 3 registrations per minute per IP, in code) applies to scripts and tests too. `process/xauth.md` § "Se connecter".
- **Virtual DocTypes, `iam`, profile (`process/iam.md`).** A DocType with `source: <name>` keeps its documents in a source registered by its plugin (`doctype_sources`, `sources.py`): the engine still applies grants, strict schema, `read_only`, links, filters/sort/search/aggregates IN MEMORY (`memory.py`, parity-tested against the SQL path in `tests/unit/test_virtual_doctypes.py` — change one interpreter and that fails), a missing source is a 503, a crashing one a 502 without detail. No history/hooks/series/files/submit for them (`schema._source_rules`). `tests/support/plugins/iam` (module `iam`, requires `auth`) exposes xauth as DocTypes `Permission` (read-only catalogue), `Role`, `Member` through `tests/support/plugins/iam/src/source.py` → IPC `xauth.iam.*` (`app/auth/src/{services/iam.py,ipc_iam.py}`; callers named in xauth's `allowed_callers`: `xcore-doctype`, `iam`, `hr`): the engine authorises, **xauth re-judges the actor** (organisation owner or platform admin writes; a plain member reads the directory only). `rbac.declare` grants may carry `default_roles` (the iam grants also go to `tenant_admin`). `User Profile` uses `naming: owner` (one document named like the user) and the special grant `@authenticated` (any identified user, never declared to auth). `hr` requires `iam`: `Employee.user` links a `Member`, hook `hr.employee_access` (`tests/support/plugins/hr/src/access.py`) closes the account when the status becomes « Parti » (refuses the save if the actor cannot). Desk: `FieldMeta.read_only`, `DocTypeMeta.virtual`, « Mon profil » (`stores/profile.ts`, `ProfileView`), Settings rail links to the Member/Role/Permission lists when readable. xauth's rate limit is now the manifest's `rate_limit:` block (`RateLimitPolicy`: `enabled: false` in tests).
- **Mail and the Desk's Settings > Système.** xauth's mail goes through the `ext.email` extension (`extensions/xmailler`, copied from donna, `services.extensions.email` in `integration.yaml`; no SMTP host = **simulated mode**: status stays READY, messages are logged and counted, never sent; `XAUTH_SMTP_*` in `.env` configures it). `app/auth/src/routes/mail.py` (`/mail/status`, `/mail/test`) is platform-admin only and never returns a secret. With xauth as login (`services.auth`, root derived from `login_url`) the Desk's Settings gets a "Système" group (`/settings/~account|organisation|users|roles|permissions|accounts|mail|audit|api`, `ui/src/components/admin/`, client `ui/src/lib/xauth.ts` = `XauthClient extends ApiClient`, `HttpMethod` includes `PATCH`) covering what a screen can do with xauth (table and the deliberate exclusions in `process/xauth.md`): xauth decides each right, a 403 is shown as "réservé", never as a failure. **xauth's JWT carries NO permissions**: `session.loadPermissions()` reads `/rbac/me/permissions` and `session.platformAdmin` (`admin:*`) only hides the platform-only rubriques (`permissions`, `accounts`, `mail`); never use it as a right. The bell (`NotificationsMenu`, `stores/notifications.ts`) shows xauth notifications: text is HTML-escaped by the server (decode to display, never `v-html`) and a link is followed only if it is `#/…` or https (`safeTarget`). A global role's permissions are added/removed by permission ID, an organisation role's by NAME (xauth's own asymmetry). `ui/e2e/look-admin.mjs` walks the pages and the bell in a real browser.
- **The Desk's auth screens (`ui/src/views/`, all `meta.public`, contracts in `process/xauth.md` § "Desk : la connexion").** `session.ts` also drives `POST …/register` (a account without an organisation), `…/password/forgot|reset`, `…/invites/token/{token}` (read WITHOUT a session) + `…/invites/accept` (with it), `GET …/oauth/providers` + `…/oauth/{p}/authorize` (nonce `app_state` kept in sessionStorage, returned on `#/oauth` by `OAuthCallbackView`), `GET …/tenants/` and `POST …/select-tenant` for the organisation switcher in `AppShell` (reload: Desk caches are per organisation). **Emails link to the DESK as a web URL** (`desk_url` = `app.desk_url`/`XAUTH_DESK_URL`/`<base_url>/app/xcore-doctype/desk/`, read in `app/auth/src/main.py`, used by the password/invite senders and the register reply): no `erp://` deep-link anywhere except xauth's default OAuth redirect target, which an operator enables with `OAUTH_WEB_REDIRECT_ORIGINS`.
- **Test auth:** the engine's tests do not start xauth: `tests/support/dev-auth/` is a TEST-ONLY HMAC token backend (named `auth`, so the repo's plugins `requires` it; `tests.support.mint_token` forges any principal; `boot_host(auth_members=…)` imitates the user directory). `tests/integration/test_xauth_real.py` boots the REAL `app/auth` (`boot_host(xauth=True)`: throwaway JWT keys, administrator from the environment) and logs in through `/app/auth/login`; `app/auth` lives on the developer's machine (untracked), so those tests and `test_username.py` **skip with a reason when it is absent**. `integration.yaml` also contains development `secret_key`/`server_key`; `app.secret_key` is the `X-Plugin-Key` for every `…/ipc/…` route including lifecycle control.
- **Sandboxed plugins can't call others** (`call_plugin` is unavailable to them), `EventBus.emit` swallows handler errors and can't veto: this is why `validate`/`before_save` are direct calls and only `after_*` will be events (phase 1).
- **A plugin whose `plugin.yaml` is not valid YAML is skipped with only a WARNING** (`invalid manifest`), so its hooks silently never register and every save of a DocType citing them answers 503 `hook_unavailable`. Quote any `description:` containing `: `.
- Logging: `xcore.kernel.observability.get_logger` with kwargs, not `logging`. **Scheduling and queues exist and are NOT optional** (checked 22 Oct 2026, `process/programme.md` §3.1): `xcdk` is a declared dependency, installed, but it **imports as `sdk`** (`from sdk import cron, interval, ScheduledMixin, task`) — `import xcdk` fails, which is why it was thought absent. xcore itself runs the scheduler (`services/scheduler/service.py`, APScheduler asyncio, `enabled` by default): `backend: redis` takes a distributed lock `xcore:sched:lock:<job_id>` so one process only runs a job, but the DEFAULT `backend: memory` has **no lock at all** — every uvicorn worker runs it. Jobs run on the app's event loop (it warns past 250 ms): trigger there, never work long there. Celery is integrated too (`services.xworker`, alias `services.celery`: broker/queues/concurrency/time limits, `@task`, `WorkerService.send`, `celery -A` for a separate worker) but `celery` is not installed here and a worker process does NOT boot the plugins — a task has no registry, no hooks, no tenant scope.
- `plugin_prefix` is `/app` in this repo's `integration.yaml` (xcore's default is `/plugin`); read it from config, don't hard-code it.
