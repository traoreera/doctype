# Phase H2 : propriétés des champs et des DocTypes, nommage, hooks, renommer, connexions, actions en lot

Palier 70 % (`doc/palier70.md`, décompte du 20 octobre 2026 : 61 lignes sur 87). Cette phase prolonge `doc/phase-h.md` (types de champ, fichiers) par ce qu'on **déclare sur** un champ ou un type, et par ce que l'utilisateur fait avec un document au-delà de l'enregistrer.

## 1. Livré

### Propriétés de champ (`schema.FieldDef`)

| Propriété | Effet | Où c'est tenu |
|---|---|---|
| `unique: true` | une valeur ne se retrouve jamais sur deux documents de l'organisation | table `xdt_unique` dont la CLÉ PRIMAIRE `(tenant, type, champ, valeur)` est la garantie : deux écritures simultanées ne passent pas toutes les deux, sur SQLite comme sur PostgreSQL (`Query.sync_unique`, dans la transaction du document). Libérée à la suppression, au changement de valeur et à l'**annulation** (l'amendement peut la reprendre). Une valeur de plus de 500 caractères est refusée nettement |
| `set_only_once: true` | libre tant qu'il est vide, figé dès qu'il a une valeur | `builder._condition_errors` (erreur `set_only_once`) ; le champ qui NOMME le document l'est d'office |
| `no_copy: true` | ni « Dupliquer » ni l'amendement ne le recopient | `DocumentService.amend`, `lib/form.duplicateValues` |
| `fetch_from: lien.champ` | la valeur est LUE du document que le Link désigne, à chaque écriture ; ce que le client envoie est écrasé | `DocumentService._fetched` (avant et après les hooks de confiance) ; la cible se lit avec les droits de l'appelant, un lien devenu illisible garde la copie d'avant ; type compatible vérifié au CHARGEMENT (`registry.fetch_incompatible` : même type, mêmes décimales, `Select` dont les choix couvrent ceux de la source…) ; ni `required`, ni `default`, ni `allow_on_submit` |
| `allow_on_submit: true` | reste modifiable quand le document est SOUMIS ; tout autre champ reste figé | `Query.update(docstatus=…)`, `DocumentService._check_frozen` (avant ET après les hooks : un hook ne dégèle rien) ; il faut `write`, pas un grant de plus ; hook `on_update_after_submit` |
| type `DynamicLink` | le DocType visé est la valeur d'un autre champ (`options: ref_type`) | `_check_links` (la cible doit exister ET être lisible, le type doit être un DocType citable) ; protège sa cible à la suppression (`registry.referrers` renvoie les `DynamicLink` avec leur `type_field`) ; suit un renommage |

### Propriétés de DocType

- **Nommage** : `naming: prompt` (l'utilisateur donne le nom ; `POST /doc/{dt}` accepte `name`, action `doc.save` `new_name`), `naming: {field: code}` (le nom EST la valeur du champ, obligatoire, jamais modifiable), en plus de `hash`, `owner` et `{series}`. `document.valid_name` : 1 à 140 caractères, ni `/ \ ? # %` ni caractère de contrôle, pas `new` (la route du formulaire de création). Un nommage automatique refuse `name` (`name_not_allowed`). Un nom pris : 409.
- **`allow_rename: true`** : `POST /doc/{dt}/{nom}/rename {new_name}` (action `doc.rename`). Brouillon seulement. UNE transaction : le document, son historique, ses commentaires, assignations, pièces jointes et valeurs uniques suivent ; chaque document qui le CITE (champ Link, ligne de table, DynamicLink) est réécrit (entrée d'historique à son nom, sans contrôle de ses droits : c'est la conséquence du renommage). Un nom pris défait tout. Entrée d'historique `rename`, événement `doctype.<nom>.after_rename`.
- **Hooks** (`schema.HOOK_EVENTS`, onze) : `before_insert` (création, dans la transaction, après `before_save`, peut modifier), `after_insert` (après le commit, avant `after_save`), `on_trash` (dans la transaction, juste avant la suppression, peut la refuser, `event.tx` pour écrire), `after_delete` (après le commit, reçoit ce que le document contenait ; événement `doctype.<nom>.after_delete`), `before_cancel` (avant `on_cancel`, même transaction), `on_update_after_submit`. Seuls `validate` et `before_save` acceptent un hook `action:` (sandboxé, hors transaction). `before_cancel` et `on_update_after_submit` exigent un DocType `submittable`. Pendant la création d'un DocType nommé par une série ou par un champ, les hooks avant insertion reçoivent `name = None`.

### Ce que l'utilisateur fait

- **Connexions** (`GET /connections/{dt}/{nom}`, action `doc.connections`) : les documents qui citent celui-ci, par type et par champ, avec leur nombre. Il faut pouvoir lire le document ; chaque type n'est compté que dans le périmètre de lecture de l'appelant (`Query.connections`, un périmètre par type), un type illisible n'apparaît pas. Les liens par les lignes d'une table se comptent mais ne s'ouvrent pas (une liste ne se filtre pas sur un tableau).
- **Actions en lot** (`POST /bulk/{dt}` `{action, names, data?}`, action `doc.bulk`) : `update` (poser les valeurs de `data`), `delete`, `submit`, `cancel` sur 100 documents au plus. Chaque document passe SEUL par la porte ordinaire (droits, validation, hooks, liens, version) : un refus ne retient pas les autres, le compte rendu dit pour chacun `ok` ou son code et son message. Le droit d'effectuer l'action est exigé UNE fois d'abord ; ne se posent pas en lot : tableaux, secrets, fichiers, champs copiés (`fetch_from`), lecture seule, cachés. `POST /assign-many/{dt}` (action `doc.assign.many`) assigne plusieurs documents à la même personne.
- **Notifications** (`notifier.py`, service `xauth.notify`) : assigner quelqu'un (sauf soi-même) et le citer dans un commentaire (`@adresse@exemple.fr`, un membre de l'organisation) sonne SA cloche. Le texte d'un commentaire ne voyage pas ; l'assignation porte la description que l'auteur a écrite POUR l'assigné ; une assignation en lot envoie UNE notification. Effet de bord pur : un xauth absent, arrêté ou qui refuse est journalisé et ne fait jamais échouer l'assignation ou le commentaire (`doctype.notifications.provider: none` les coupe). Côté xauth (`app/auth/src/ipc.py`, `xauth.notify`) : seuls les membres de l'organisation demandée reçoivent, le lien doit commencer par `#/` ou `https://`.

### Desk

- Formulaire : champ **Nom** à la création d'un type `prompt` ; **Renommer** (boîte, les liens suivent) ; **Dupliquer** (`?copy=`, un formulaire neuf pré-rempli sans l'unique, le `no_copy`, le secret, les fichiers, les champs `fetch_from` ni le champ de nommage ; les champs lus d'un lien se montrent tout de suite) ; champ copié **affiché en lecture seule et mis à jour dès qu'on choisit le lien**, avant même d'enregistrer ; `set_only_once` et champ de nommage en lecture seule une fois enregistrés ; document soumis : seuls les champs `allow_on_submit` restent saisissables (bandeau dédié) ; lien dynamique (champ désactivé tant que le type n'est pas choisi, valeur effacée si le type change) ; panneau **Connexions**.
- Champ Link : **« + »** à côté du champ (saisie rapide : les champs obligatoires et le titre, ce qui était tapé devient le titre ; un type qui exige un tableau, un fichier ou une obligation conditionnelle ouvre sa fiche complète à part) ; **aperçu au survol** de la flèche « ouvrir » et d'un lien en lecture seule (titre et quatre champs, rien n'est lu avant le survol).
- Zone de commentaire (`CommentComposer.vue`, `lib/mentions.ts`) : **`@`** propose les membres de l'organisation (`GET /mentionable/{dt}/{nom}`, action `doc.mentionable` : il suffit de pouvoir LIRE le document, pas de l'écrire ; seuls les membres avec adresse, jamais l'auteur ; une lecture après 150 ms de pause) et insère `@adresse ` (exactement ce que le serveur reconnaît pour prévenir le membre) ; **`/`** (en début de ligne ou après une espace) propose des commandes sur le document, jugées sur les droits : `/assigner` (boîte d'assignation), `/joindre` (choix de fichier), `/mention` (laisse un `@` et ouvre la liste), `/terminer` (clôt MES assignations ouvertes sur ce document). La commande disparaît du texte et n'est jamais envoyée. Clavier : flèches, Entrée ou Tab pour choisir, Échap pour fermer (la même mention ne se rouvre pas à chaque lettre), Ctrl+Entrée envoie. Les mentions d'un commentaire s'affichent en évidence (du texte, jamais du HTML). En modifiant un commentaire, `@` marche, pas `/`.
- Liste : **barre latérale** (valeurs et nombre de documents des trois premiers champs Select/Link/Booléen, dans les filtres en vigueur sauf les siens, un clic filtre, un second retire) ; cases à cocher pour toute action en lot possible, **menu Actions** (modifier un champ, assigner, soumettre, annuler) et suppression en lot, avec compte rendu des refus.
- **Documentation de l'API** (`#/api/<Type>`, `lib/apidocs.ts`) : routes que l'utilisateur peut employer (jugées sur ses droits), `curl` à copier, champs (type, bornes, opérateurs de filtre, règles), exemple de document. Générée de la définition : un champ ajouté apparaît sans rien écrire.
- Le plugin d'essai `lab` montre chaque propriété (`Place` renommable, `Visit` avec `fetch_from`, `unique`, `set_only_once`, `no_copy` et lien dynamique, `Badge` nommé par son code, `Memo` nommé à la saisie, `Voucher` soumettable avec suivi).

## 3. Limites

- `unique` ne regarde que les documents écrits depuis qu'il est déclaré : un champ rendu unique APRÈS coup n'a pas de ligne pour les documents existants (le premier qui en réécrit un les réserve). Pas de reconstruction automatique, pas de contrôle des doublons déjà présents.
- Une valeur unique se compare à la lettre (« Ada » et « ada » sont deux valeurs).
- Renommer : brouillons seulement ; les documents qui citent l'ancien nom sont réécrits sans contrôle de leurs droits, y compris ceux qui sont soumis (leur historique garde la trace) ; pas de hooks `before_rename` / `after_rename` (seulement l'événement).
- `fetch_from` : pas de recopie vers un champ Link, fichier ou tableau ; un document soumis ne relit plus ses liens.
- `DynamicLink` : si le champ de type est un `Select`, ses options doivent être des DocTypes DÉJÀ chargés au moment du chargement du plugin (même règle qu'une cible de Link : le plugin les apporte ou en `requires` un) ; avec un `Text` libre, rien n'est vérifié avant la saisie.
- Actions en lot : 100 documents, un par un (pas une seule requête SQL) ; modifier en lot ne touche pas aux tableaux, secrets et fichiers ; « étiqueter » n'existe pas (les étiquettes sont un autre chantier).
- Mentions : par adresse e-mail ; la liste proposée vient de l'annuaire d'xauth, gardé 60 s par le moteur (un membre tout neuf n'y est pas tout de suite) ; une personne citée est prévenue même si elle ne peut pas lire le document (elle ne voit que son type et son nom, le lien lui répond « introuvable »). Les commandes `/` sont quatre, toutes sur le document : pas de mise en forme (un commentaire est du texte brut).
- Barre latérale : trois champs, choisis par le Desk (pas configurables) ; pas de regroupement par propriétaire ni par étiquette.
- Documentation de l'API : pas de schéma OpenAPI par type, pas d'exécution depuis la page.
- Deux rejets de promesse non gérés (`insertBefore` d'un nœud nul) apparaissent à l'exécution de `vitest` en suite complète, attribués à `collab.spec.ts` (le montage d'une carte de pièces jointes finit de s'afficher après la fin du test). Ils apparaissent aussi sans les nouveaux fichiers de test de cette phase, et seuls les fichiers complets les montrent ; aucun test n'échoue, mais la cause n'est pas établie.
